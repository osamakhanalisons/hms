1. Project Overview

AT-BMS HousingOS is a browser-based Building and Society Management System for gated communities, apartment complexes, housing societies, and commercial buildings. It centralizes resident records, property units, billing, payments, complaints, visitor access, documents, notices, assets, vendors, audit logs, and management reporting.

System TypeMulti-tenant web application that can run many societies on one platform while keeping each society's data separate.
FrontendReact application using TanStack Router, role-aware navigation, dashboard screens, tables, forms, and status panels.
BackendTanStack Start server functions handle authentication, database reads, writes, permissions, module gates, and business workflows.
DatabaseMySQL stores users, tenants, property hierarchy, ledger entries, payments, complaints, security logs, and operational data.

2. Access and Login

  1. Open the application URL in a browser, for example http://localhost:5173/.
  2. Enter the registered email address and password on the login page.
  3. The system validates the credentials, creates a secure session, and loads the user's profile.
  4. The sidebar and dashboard are generated according to the user's roles, permissions, active modules, and active society.
  5. If a user manages multiple societies, they should confirm the selected active society before entering or updating records.
  6. Use logout when work is complete so the session is closed safely.
Important: Users should never share accounts. Every admin, resident, guard, finance user, and technician should work from their own assigned login.

4. Complete System Flow

1. Society SetupSuper Admin creates a tenant and assigns modules.
2. Property SetupBlocks, buildings, floors, and units are created.
3. User SetupAdmins, residents, guards, technicians, and finance users are assigned.
4. Daily OperationsBilling, payments, complaints, visitors, notices, and assets are managed.
5. Review and AuditReports, dashboards, and audit logs are used for control.

Core Data Hierarchy

Society / Tenant -> Block -> Building -> Floor -> Unit -> Resident

The tenant is the highest level of separation. A society owns its property tree, users, residents, financial records, complaints, visitors, documents, and reports. Unit-level records such as residents, bills, payments, and complaints should always be linked to the correct unit so reports and dashboards remain accurate.

5. Daily Operating Flows

Monthly Billing FlowSet charge heads, run monthly charges, review generated ledger entries, record resident payments, then export statements or reports.
Complaint FlowA resident submits a complaint, admin reviews it, priority/status is set, technician is assigned, work is completed, and the ticket is closed.
Visitor FlowA resident creates a visitor pass, the guard verifies it at the gate, entry is recorded, exit is recorded, and blacklist checks protect the society.
Notice FlowAdmin writes an announcement, publishes it to the notice board, residents read it, and notifications can alert relevant users.

Societies

/societies
Image: Add manual-images/module-societies.png showing society list, create society button, plan/status badges, and admin mapping.

Used by: Super Admin and authorized administrative users.

  5. Save the society, switch into its context, and begin property setup.
  6. Deactivate or lock a society only when access must be suspended.

Used by: Society Admin and authorized property staff.

8. Security and Permissions

  • Every request is resolved through the active authenticated session.
  • Tenant-scoped records must be filtered by tenant_id so one society cannot access another society's data.
  • The sidebar hides modules when the user has no view permission or when the module is inactive for that society.
  • Role permissions can control can_view, can_create, can_edit, and can_delete.
  • Module activation gates prevent disabled modules from being used even if the route is opened directly.
  • Audit logs preserve important administrative actions for accountability.
  • Production passwords, database credentials, and API keys should never be written in public manuals.
Security rule: Always test permission changes using a lower-privilege account before handing access to real users.
